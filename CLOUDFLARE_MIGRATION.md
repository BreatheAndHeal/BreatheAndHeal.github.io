# The Unsaid: Cloudflare migration notes

This document is the Cloudflare migration and operations runbook. The owner currently uses `migration/cloudflare-preview` for the Cloudflare Pages deployment at `https://the-unsaid-bg2.pages.dev`. A successful CI smoke test validates build and route guards; it is not proof of a complete Razorpay → Neon → Google Calendar/Meet/email transaction. Keep the end-to-end checklist below as a gate for final promotion and future major production changes.

## Architecture

- Static site output: dist/ (generated by npm run build)
- Cloudflare Pages Functions: functions/api/
- Existing booking/payment handlers and business logic: api/ and lib/
- Existing PostgreSQL database: Neon (retain initially; no schema conversion in this migration)
- Existing Google Apps Script calendar/email integration: retain initially
- Payments: existing Razorpay account and order/webhook integration

The build script intentionally excludes api/, lib/, functions/, scripts/, schema files and configuration from public static assets. API source files should not be copied into dist/.

## Required Cloudflare Pages environment variables

Configure values in Cloudflare Dashboard > Workers & Pages > the Pages project > Settings > Variables and Secrets. Never commit secret values or paste them into chat.

Set the non-secret build variable `PUBLIC_SITE_URL` to the exact final HTTPS origin. Example: `https://the-unsaid.pages.dev` only if that is the actual assigned project URL. The build intentionally fails without this variable and rewrites page canonical/social metadata, sitemap, and robots.txt to that origin. If Cloudflare assigns a different `pages.dev` name, use that exact origin instead.

Keep the non-secret build variable `SITE_INDEXING_ENABLED=false` throughout staging and testing. The static output will send `X-Robots-Tag: noindex` until final launch. Only after all critical production tests pass, set `SITE_INDEXING_ENABLED=true` for the production environment and redeploy; API responses remain `noindex, nofollow`.

Required for the current code:
- DATABASE_URL — existing Neon PostgreSQL connection string
- Shared database table `api_rate_limits` — created from the additive schema in `schema.sql` before deploying the shared rate limiter.
- RAZORPAY_KEY_ID — test key for preview; live key only after testing is approved
- RAZORPAY_KEY_SECRET — secret
- RAZORPAY_WEBHOOK_SECRET — secret matching the configured Razorpay webhook
- GOOGLE_APPS_SCRIPT_SECRET — secret matching the Apps Script deployment
- ALLOWED_ORIGIN — exact production website origin, e.g. https://the-unsaid.pages.dev
- BOOKING_TIMEZONE — Asia/Kolkata
- MIN_LEAD_MINUTES — 60

The current schedule is intentionally enforced in `lib/config.js`: 07:00–23:00 IST, every day including Sunday, with 20-minute start intervals. Stale schedule environment variables are ignored by design; schedule changes require a code change and tests.

Optional:
- GOOGLE_APPS_SCRIPT_URL — if configured, use the exact Apps Script deployment URL stored privately in the existing environment; otherwise the source has a fallback URL.

The site must use relative same-origin API paths (/api/...). Do not store secret values in frontend variables, HTML, or build-time public variables.

## Staging data isolation is mandatory

Do not configure the staging project with the production `DATABASE_URL`, production Razorpay keys, or the production `GOOGLE_APPS_SCRIPT_SECRET`. A captured Razorpay Test Mode payment still drives the booking confirmation code; if staging shares production data/calendar credentials, it could create real database rows, locks, Calendar events, and emails.

Before end-to-end payment tests:
- Create a separate empty Neon test database/project and apply `schema.sql`; do not clone real customer booking data merely for testing.
- Use Razorpay **Test Mode** credentials and its matching test webhook configuration.
- Use a separate Apps Script deployment connected to a dedicated test Google Calendar, with a separate secret and test-only email recipients. If this is not ready, do not claim the end-to-end booking test has passed.
- Configure preview/test secrets only in the staging environment. Keep production credentials in the production environment, and do not paste either set into chat.

Only after tests pass should the production environment be switched to the existing production database, approved live Razorpay keys/webhook secret, and the current production Apps Script secret. The old live website remains available during staging.

## Required verification before production cutover

1. Confirm the preview site loads all pages and static assets; confirm API source files are not publicly served as static files.
2. Test API endpoint method restrictions, invalid JSON, missing consent, invalid date/session, rate-limit responses, and origin handling.
3. Test availability against both Neon slot locks and the real Google Calendar.
4. Test Razorpay Test Mode order creation, invalid signature rejection, amount mismatch rejection, and captured-payment webhook signature validation.
5. Test duplicate webhook/browser verification events; there must be no duplicate booking or Calendar/Meet event.
6. Test failed/abandoned payment, expired hold cleanup, conflicting bookings, and paid-but-pending Calendar recovery.
7. Confirm meeting-link and email delivery, mobile and desktop booking, legal/contact links, reduced-motion behavior and basic accessibility.
8. Confirm shared rate limiting works across requests/instances and review Cloudflare/Vercel runtime errors after deployment.
9. Confirm expired unpaid booking details are anonymized after the 90-day retention window; do not manually delete current booking/payment rows without checking reconciliation state.
10. Export/backup the database and code before switching production. Keep the old site/backend online until all critical tests pass.

Do not delete GitHub Pages, the existing Vercel project, the Neon database, or existing secrets until the new deployment and rollback path are verified. This branch is intentionally separate from main.
